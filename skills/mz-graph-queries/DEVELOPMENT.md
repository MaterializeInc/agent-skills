# Developing this skill

How mz-graph-queries was built, what was measured while building it, and how to
test a change to it. The runnable harness lives at `evals/mz-graph-queries/` in
the agent-skills repository, the one this skill is published in; its README
covers operation. This file covers the method.

The rule the reference files were written under: every behavioral claim traces
either to one of those sources or to a SQL block in this skill that the
verifier runs and compares against recorded output. A claim that is neither is
removed, not softened. Where a source and the emulator disagreed, the emulator
won and the disagreement is written down (see below).

## The fixture

There is one world, and every reference block and every eval task runs against
it: `references/fixture.sql`, generated by
`evals/mz-graph-queries/build_fixture.py --small`. Do not edit it by hand;
regenerate it. The eval-scale fixture comes from the same generator with a
larger `--scale`.

| Tables | Shape | Families |
|---|---|---|
| `employees` | tree, one root, eight people | descendants, ancestors, depth, root, ordered display, salary rollup |
| `parts`, `bom` | DAG with quantities | BOM explosion, kit cost, shared-component counting |
| `accounts`, `transfers` | directed, cyclic, timestamped | reachability, k-hop, cycle audit, SCC, expiring edges |
| `groups`, `memberships`, `permissions` | tree with an override | permission inheritance, `NOT EXISTS` override, point check |
| `customers`, `customer_links` | undirected, scored | components, entity resolution, thresholds |
| `cities`, `roads` | undirected, weighted | hop count, weighted shortest path, witness path |
| `pipelines`, `depends_on` | DAG | topological level, downstream and upstream impact |

The traps are deliberate and every one of them is a real failure an agent
makes: a bolt shared between the wheel and the frame, so `UNION` and
`UNION ALL` give different totals; a payment ring, so a counter-carrying
closure diverges; an explicit grant below an inherited one, so a naive
inheritance query returns two levels for the same document; customer links
stored one way, so an unsymmetrized component query splits a cluster; roads
stored one way, so a route query finds no path back; and a road network in
which the fewest-hops answer and the cheapest answer disagree, so a query that
conflates the two is visibly wrong. The eval-scale fixture adds a detached
3-cycle of managers to the org tree.

## Verification

`evals/mz-graph-queries/verify_skill_sql.py` extracts every fenced ```sql block
from `references/*.md`, runs it against a freshly loaded fixture schema, and
diffs the result against `expected/<file>/<NN>.txt`. It reads `references/`
only; `SKILL.md` is not executed.

```bash
cd evals/mz-graph-queries && python3 verify_skill_sql.py
```

Success prints `OK  (9 file(s), N block(s))`. Conventions in the markdown:

- Only ```sql fences run. Blocks in another dialect are fenced ```postgresql or
  similar and are skipped, which is how `migrating.md` shows the source query
  next to its translation.
- `<!-- verify: error -->` immediately above a fence means the block must fail,
  and its `ERROR` line is compared against the recording. Several claims in the
  skill are held up by these.
- `<!-- verify: skip -->` means the block is not run. Use it only for blocks
  that name objects outside the fixture, such as the relationship-registry
  example in `context-graphs.md`, or that are fragments rather than runnable
  statements, such as the shared `sym` binding quoted in `shortest-paths.md`.
  The skeleton in `SKILL.md` carries the same marker, for the first reason.

Of the 81 `sql` blocks in `references/`, the verifier runs 79: two are skipped,
and ten of the 79 are `verify: error` blocks whose failure is the claim.

Re-record with `--record` (optionally `--only <file>`) when the block itself
changed and the new output is correct, or when a Materialize upgrade changes
`EXPLAIN` text. Never re-record to make a red block green: read the diff first,
because the recorded outputs are the skill's claims.

## Behaviors measured during development

All of these were measured on the Materialize emulator v26.38.1 while writing
the reference files, and each one is stated with its evidence in the file
named. Two of them look like defects worth reporting upstream.

1. **`ERROR AT RECURSION LIMIT` tracks changes to the row set, not to values.**
   A binding topped by a reduce or a TopK raises while it is still adding or
   removing rows, then goes silent once only its values keep changing, and
   returns the iteration-n state with no error. This affects exactly the shapes
   that most need a guardrail: min-label propagation, shortest paths with `min`
   inside, and rollups with `sum` or `max` inside. The skill therefore splits
   the guard by shape: `ERROR AT` for `UNION`-topped traversals, `RETURN AT`
   plus a check on the returned state for reduce-topped ones
   (`references/semantics.md`, Recursion limits). **Probable bug; worth
   reporting upstream.**
2. **A limited recursion over cyclic data hydrates and serves.** A materialized
   view of a reduce-topped level query over a cycle installs, hydrates,
   reports `hydrated = t`, and returns iteration-n counters that are
   indistinguishable from real levels. Only the unlimited form behaves the way
   an unconverged view is expected to, holding a dataflow and never hydrating
   (`references/reachability.md`, Topological level on a DAG).
3. **A nested WMR block in a scalar subquery aborted `environmentd`.** The
   derived-table form, `FROM (WITH MUTUALLY RECURSIVE ...) AS x`, works and is
   what the skill teaches (`references/semantics.md`, Pitfalls). **Probable
   bug; worth reporting upstream.**
4. **`EXPLAIN` linear chains is rejected for recursive plans.** The syntax is
   `EXPLAIN OPTIMIZED PLAN WITH (linear chains) AS TEXT FOR ...`, and on a WMR
   query it returns `The linear_chains option is not supported with WITH
   MUTUALLY RECURSIVE` (`references/semantics.md`, Reading EXPLAIN).
5. **Typing is stricter than it looks.** A bare `NULL` and a string literal
   both type as `text` in a binding, so both fail against any other declared
   type before anything runs, and declared typmods apply as assignment casts
   that change values (`numeric(38,2)` rounds) (`references/semantics.md`,
   Column types). Relatedly, `least()` ignores NULLs, which is what lets a
   singleton fall back to its own label in the SCC block
   (`references/components.md`, Strongly connected components from the
   closure).
6. **Predicates are never pushed into a recursive binding.** Hop bounds,
   temporal filters and pruning all have to be written inside the binding; in
   the body they filter an answer the loop already computed in full
   (`references/semantics.md`, What the optimizer will not do).

## Version-sensitive recordings

Some expected outputs are properties of v26.38.1 rather than of the pattern,
and they are the first things to check after a Materialize upgrade.

- The `EXPLAIN` recordings in `semantics.md` (Reading EXPLAIN) and
  `hierarchies.md` (the maintained closure table). Operator names and plan
  layout drift between versions; the shape the prose describes should survive,
  the text may not.
- The recursion-limit demonstrations that record iteration-n state rather than
  a fixpoint: the aggregate-inside rollup in `rollups.md`, the cyclic
  topological level in `reachability.md`, the negative-cycle distance in
  `shortest-paths.md`, and the threshold and trim blocks in `components.md`.
  Every one of those recordings exists because the limit did not fire. If a
  future version makes `ERROR AT` value-aware, these blocks start erroring, the
  verifier goes red, and the guard advice in `SKILL.md` Step 4 and in
  `semantics.md` needs rewriting rather than re-recording.

## The evaluation

Designed, not yet run; the harness lands with the eval tasks and the recorded
results table goes in `evals/mz-graph-queries/README.md`.

One graded run is a single authoring round against the eval-scale fixture. The
agent gets about fourteen prompts, one per family and one per planted trap:
descendants of a manager whose data has a loop, total kit cost where a bolt
appears under two assemblies, accounts within three hops of a flagged account
phrased as "all paths", effective document access with an override, customer
clusters above a score threshold, cheapest route with one witness path,
downstream pipelines affected by a change, a colleague's `UNION ALL` closure
that never returns and has to be fixed, and a maintained view that must stay
correct after a mutation.

Grading is automatic where it can be. `grade.py` diffs the agent's views
against independent Python answer keys in `reference.py`, applies each task's
mutation script, re-diffs, checks convergence through hydration status, and
reads the guardrail out of the view definition. The manual axes are in
`rubric.md`: initial correctness, post-mutation correctness, convergence and
guardrails, maintainability, and explanation.

Clean-room rules carry over from `evals/mz-optimize-memory`: the agent's only
route to the database is a generated `psql` wrapper pinned to the run's schema,
read-write within it and nothing outside it; no network; no skills except the
one under test; answer keys structurally unreachable rather than merely
unmentioned; ancestor `CLAUDE.md` files refused; auto memory disabled. Run
`preflight.sh` before a batch and after any harness or CLI upgrade. A cell is
one model under one condition, run by `run_cleanroom.sh`, and cells are run one
at a time.

## Testing a change to the skill

1. Edit the skill files.
2. Run `python3 verify_skill_sql.py` from `evals/mz-graph-queries/`. Every
   block must pass before anything else is worth doing. If you changed a block,
   read the diff before you re-record it.
3. Run at least one skill-condition cell and one bare cell, and compare them
   against the recorded table in the eval README. For a targeted edit, prefer
   re-running the cell that previously failed at exactly the behavior the edit
   addresses; a fixed cell is the cleanest evidence a skill change works.
4. Run a usability pass: give a fresh agent the skill and a disposable fixture
   schema, and ask it to report ambiguous, incorrect or misleading skill text
   alongside its answers. Verify every claim that agent makes about Materialize
   before baking it in; agents' reports rest on false observations often
   enough to matter.
5. Re-verify the version-sensitive recordings above against the Materialize
   version you are on, and check that the guard advice still matches what the
   limits actually do.
